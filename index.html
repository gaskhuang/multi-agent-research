多 Agent 協作 — 六條黃金法則

三份報告中一致認同的核心原則

1 分工不明確 = 混亂

每個 Agent 必須有明確的職責邊界。最失敗的多 Agent 系統往往不是技術問題，而是角色重疊導致重複工作或互相覆蓋。使用「Router → Specialized Workers」或「Orchestrator → Sub-agents」模式，每個子任務只交給一個 Agent。

2 共享記憶體是必要基礎設施

Agent 之間不能各自為政。需要共享的 context window、message bus 或外部知識庫（如向量資料庫），讓 Agent A 的產出能被 Agent B 即時取用。無共享記憶體的架構注定資訊孤島。

3 人的監督不是瓶頸，是安全閘門

完全自主的多 Agent 循環在當前階段仍然危險。最好的設計是「Agent 提案 → 人確認 → Agent 執行 → 人審查」的循環。關鍵節點（金流、寫資料庫、對外發文）必須有 human-in-the-loop。

4 選擇框架要看你的約束條件

CrewAI 最快上手適合 MVP；LangGraph 最靈活適合複雜 DAG；AutoGen 分散式支援最好；OpenAI Agents SDK 最適合 OpenAI 生態系。沒有最好的框架，只有最適合你約束條件的框架。

5 Agent 間通訊成本不可忽略

每次 Agent 之間傳遞訊息都有 token 成本和延遲。過度頻繁的通訊會讓系統變慢、變貴。設計原則是：非同步通訊 > 同步通訊；批次傳遞 > 逐條傳遞；只傳必要資訊，不傳完整 context。

6 可觀測性是第一生產力

多 Agent 系統的 debug 難度是單 Agent 的平方級。必須有：log trace（誰做了什麼、為什麼）、狀態檢查點（每個 Agent 的產出可回滾）、cost tracking（每個 Agent 花多少 token）。沒有可觀測性就不要上 production。

本次實驗的 Meta 教訓

同步執行三 Agent 研究本身就是一次多 Agent 協作實驗

⏱ 速度 vs 質量取捨

  • 三 Agent 平行執行總耗時約 4 分鐘 — 比序列執行快 3 倍
  • 但整合三份報告需要額外處理衝突（不同 Agent 對同一框架評價不一）
  • 結論：平行適合探索性研究，序列適合需要一致性的合規任務

🔄 模型差異是真實的

  • 同樣的 prompt，DeepSeek V4（Hermes）產出最精煉；Claude（Claude Code）最長最完整；GPT 5.5（Codex）技術細節最多
  • 不同模型對同一主題的「what matters」判斷不同 — 這是互補優勢
  • 結論：多模型架構比單模型多 Agent 更有價值

🔧 工具鏈整合是難點

  • 三種 Agent 使用不同的工具集（web search、文件讀寫、程式執行）
  • 跨 Agent 的產出格式不一致，需要格式標準化層
  • 結論：多 Agent 系統需要統一的產出 schema / template

結論：多 Agent 不是噱頭

本次實驗本身就是最好的證明

三個不同的 Agent 同時研究同一個主題，各自產出具有互補價值的報告。Hermes 給出決策者可立即使用的黃金法則，Claude Code 提供完整的知識框架，Codex 深入技術細節。整合後的報告品質遠超任何單一 Agent 的產出。

多 Agent 協作不是時髦的口號，而是在當代 AI 能力限制下最務實的提升方式。

每一個模型都有自己的長處與盲點。與其等待一個完美的通用模型，不如讓多個 Agent 協同工作，彼此補足短板。

「三種 Agent 的平行研究不僅產出了更好的結果，更讓我們親身驗證了多 Agent 協作的方法論 — 這是用 meta 層級的方式證明自己的論點。」
